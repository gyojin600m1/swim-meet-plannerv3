# 引き継ぎ書 — パシャ家計 レシート取り込みワークフロー

Codex（または他の実装者）がこのディレクトリを初めて開く前提で、ゼロから
説明する。既存の会話ログは参照できない前提で書いてある。

## 1. これは何のワークフローか

「パシャ家計」という個人の家計簿アプリ（Claude Artifact として公開済み）に、
紙のレシート写真から支出明細を自動入力する作業。ユーザーは紙レシートを
スマホで撮って送るだけで、あとは読み取り → カテゴリ分け → DB書き込みまで
自動で行う。

ユーザーはパシャ家計アプリ**内蔵**のAIカメラスキャン機能を意図的に使って
いない（精度が低いため）。この「チャット越しに読み取って書き込む」経路が
唯一の運用方法になっている。

## 2. 最初に理解すべき制約（最重要）

**このワークフローの最終書き込み先（パシャ家計のデータベース）は、
Claude Artifacts 基盤に固有のものであり、このリポジトリにも、一般的な
Firebase/REST API にも存在しない。**

- アプリ本体（`pasha-kakei.html`）はこの git リポジトリの外、
  `https://claude.ai/code/artifact/bcc8e2fc-5b86-4d76-83d3-a8aaf0c561a4`
  という Claude Artifact として公開されている。
- そのデータストア（`transactions` コレクションなど）は、本物の Firebase
  プロジェクトではなく、Anthropic がホストする Claude Artifacts の
  「db capability」という機能で、Firestore ライクな API
  （`collection().add()` / `doc().set()` / `onSnapshot()`）をアプリの
  JS に提供しているだけ。サービスアカウントや接続文字列は存在しない。
- このデータへの読み書きは、Claude 側の `Artifact` ツール
  （`action=read_db` / `action=write_db`）を持つセッションからしかできない。
  Codex が同等のツール連携を持っていない限り、**Codex から直接このDBに
  書き込むことはできない。**

### 現実的な分担案（ユーザーと要相談）

1. **（推奨）読み取り・検証は Codex、最終コミットは引き続き Claude。**
   Codex は本書のルールとスクリプトで「レシート写真 → 検証済みJSON」まで
   作り、その JSON をこのリポジトリ（または別の受け渡し場所）に置く。
   実際の `write_db` 呼び出しは、Artifact ツールを持つ Claude セッションが
   最後に行う。
2. パシャ家計を本物の Firebase などに移行し、Codex にもサービス
   アカウント等で書き込み権限を渡す（アプリ側の作り直しが必要、未着手）。
3. Codex 側に Claude Artifacts 相当の統合がある場合はそれを使う（要確認）。

どの道を取るか決まっていないので、**Codex に最初に確認させること。**
以下のセクションは、どの分担になっても共通して必要な部分（読み取りの
正しさ・データ形式・既存データ）をまとめたもの。

## 4. データモデル

1レシート = 複数の「取引ドキュメント」（1品目1ドキュメント）。

```json
{
  "type": "expense",
  "date": "2026-09-04",
  "yearMonth": "2026-09",
  "category": "food",
  "amount": 5080,
  "memo": "国産塩さば切身",
  "store": "業務スーパー 谷山店",
  "receiptId": "rcpt-20260904-5080",
  "source": "receipt",
  "createdAt": "2026-09-04T00:00:00.000Z"
}
```

複数個をまとめた行（後述）には `qty` と `unitAmount` も付く。

カテゴリIDは `SKILL.md` の「Category IDs」節が正本。ユーザー独自の
カスタムカテゴリが1つ存在する：`custom_car7a1f3`（🚗 カー用品 — 自家用車の
エンジンオイル・廃油処理・ガソリン・車検など）。新しいレシートで未知の
カテゴリIDを使う前に、必ず `settings/categories` ドキュメント相当の
最新状態を確認すること（Codex 側から見えない場合はユーザーに確認）。

ドキュメントIDの形式は `rcpt-<YYYYMMDD><総額>-<NN>`
（例: `rcpt-202609040238-01`）。同じレシートを再インポートすると
上書きになる（content-derived ID）ので、重複チェックの保険にもなる。
ただし主たる重複チェックは「同じ store + date + 合計」で行う
（`SKILL.md` 手順2）。

## 5. 読み取りルール（要約 — 詳細と具体例は SKILL.md）

日本のスーパー・ドラッグストアのレシートを正しく拾うための、実レシートで
踏んだ地雷から得たルール。全文は `SKILL.md` の「Reading rules」節。

1. **割引行は直前の品目に畳み込む。** `割引20% -60` は独立した行ではない。
   まとめ割引（`(3点 1回) -46` のような表示）は**1回だけ**差し引く —
   2行に分かれて印字されても同じ値引きの言い換え。
2. **個数行（`(3個 x @88)`）は印字済みの合計。** そのまま1行として扱う。
   品名には `×N` を付けて個数が分かるようにする。
3. **同一商品の繰り返しスキャンは `品名 ×N` の1行にまとめる。**
   ユーザーの指示：「明らかに同じものなら✖️10でシンプルでいい」。
   ただし同じ品名が離れた2行に分かれて印字されることがあり（1回目が
   N個分、2回目が単独の追加1個など）、見落としやすい。**税率帯
   （`税率N%対象額`）と突き合わせて、合計が合うかで判断する。**
4. **小計・合計・外税額・買上点数などフッター情報は品目ではない。**
5. **外税receiptは税込みに換算してから書き込む。** 小計 ≠ 合計 なら外税。
   店名では判断しない、必ずそのレシートのフッターで判断する。
   `scripts/grossup.py` が最大剰余法で端数なく換算する。
6. **税率マーク（`外8`/`内8`/`◆`/`※`/`*` など、店ごとに異なる）が
   最も信頼できる手がかり。** 8%は人間用の飲食料品、10%は非食品
   （酒・ペット用品・日用品など）であることが多い。店の凡例
   （レシート下部の説明文）を都度確認する。
7. **品名キーワードは税率チェックの後に適用。** 酒・ペット用品・日用品・
   医療品・カー用品のキーワードリストは `SKILL.md` 参照。読み取れない
   品名はユーザーの標準指示により `food` にする。ただし**読める品名で
   中身が分からないだけの10%品目は、勝手に `food`/`daily` に決めず、
   金額が大きければユーザーに確認する**（過去に¥4,673のカー用品を
   日用品に誤分類した事例あり）。

**検算は毎回必須。** 品目合計が印字された小計/合計と1円まで一致するか、
外税なら各税率帯合計が印字された `税率N%対象額` と一致するか、
買上点数（あれば）が品目数と一致するかを確認してから初めてDB候補とする。
合わないまま書き込まない。

## 6. スクリプトの使い方（そのまま動く）

両方とも Python 3 標準ライブラリのみ、外部依存なし、Claude 依存なし。

```bash
# 外税レシートの場合はまず税込み換算
python3 scripts/grossup.py exclusive.json > receipts.json

# パース済みレシート（内税ならそのまま、外税ならgrossup.py の出力）を
# ドキュメント形式に変換し、残高チェック・カテゴリ検証を行う
python3 scripts/build_batch.py receipts.json --out-dir /path/to/out \
  --extra-categories custom_car7a1f3
```

入力JSONの形は各スクリプトの docstring 冒頭を参照（そのまま仕様書になる）。
`build_batch.py` は

- レシート合計が品目合計と一致しない
- 未知のカテゴリIDを使っている（`--extra-categories` で明示的に許可した
  もの以外）
- 金額が0以下

のいずれかがあれば **非ゼロ終了コードで中断**し、何も書き出さない。
出力は `<out-dir>/docs/<doc_id>.json`（1ドキュメント1ファイル）と
`<out-dir>/batch_NN.json`（50件ごとのバッチ、`write_db` にそのまま渡せる形）。
